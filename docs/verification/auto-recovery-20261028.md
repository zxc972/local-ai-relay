# 工作中收信与自动恢复验证

日期：2026-10-28。范围：`local-ai-relay_local` 开发副本；未切换在线服务。

## 实现

- 已绑定 `session_id` 的 v2 自动收件会话启用恢复；未绑定旧接入保持原行为。
- 原生后台任务模式在 receive 返回中提供 `before_work=true`，要求先挂下一次等待，再执行当前工作。旧批次仍在处理时后续消息保留在数据库，确认后通知下一批。
- 回调监听新增普通父进程，工作子进程异常退出后自动重启。沿用成员、监听代次、消息 ID、批次及回执，不重新发送任务；连续失败最多重启三次，leave 会停止整个监听。
- 已接受但未收件的通知、结果不确定的通知，以及积压在旧批次后的新消息，使用单独的 `receipt_recovery` 事件核对。事件没有任务正文，中间件不调用 receive/ack、不修改任务处理结果。
- 恢复最早等待 60 秒，后续退避到 5 分钟、15 分钟，每个未发生进展的状态最多三次提醒。预算持久化，重连或子进程重启不重置。明确忙碌且尚未开始回合的拒绝不消耗提醒次数，后台稍后重试。
- 达到上限仍未解决时显示“需核对收件”；不清掉消息、不虚假确认。HTTP 页面能展示当前客户端的恢复状态；对旧服务不发送其不支持的新参数。

## 故障模拟结果

`tests/test_chat_recovery.py` 共 14 项测试。使用临时 SQLite、真实临时 HTTP 服务、真实 CLI 后台任务和真实父/子进程；宿主由测试代码模拟，不连接真实 Codex/Claude，不调用模型。

| 场景 | 接入 | 实际断言 | 结果 |
| --- | --- | --- | --- |
| A 工作中到达 B，A 完成却漏 ACK | 本地与 HTTP | 忙时 B 不执行；核对 A 的实际文件记录后补 ACK，继续 B；文件仅写入 A、B 各一次 | 通过 |
| A 已执行，但通知返回 uncertain | 本地与 HTTP | 不重发原任务；恢复后 A、B 的实际文件副作用各一次 | 通过 |
| 宿主接受通知但没 receive | 本地与 HTTP | 只发恢复提醒，原消息首次领取一次并完成，原通知不重发 | 通过 |
| 不知道 A 是否执行、无法证明结果 | 本地与 HTTP | 三次提醒后停止增加提醒，A 未被自动 ACK，B 仍在队列，页面/状态可见异常 | 通过 |
| 处理 A 前已预挂下一次宿主任务 | 本地与 HTTP、真实 CLI 子进程 | A 未确认时子进程继续等待；ACK A 后收到 B，不需要在 ACK 后再次挂起 | 通过 |
| 回调工作子进程被强制结束 | 本地与 HTTP、真实子进程 | 父进程自动启动新 PID，监听代次不变，已接受的 A 不重新通知，随后 B 正常通知 | 通过 |
| 预算持久化 | SQLite 重开/迁移 | 已保留的三次提醒预算不被重置；新的进展状态才建立新预算 | 通过 |
| 子进程反复启动失败 | 模拟进程启动失败 | 初始启动加三次恢复后停止，错误可见，不无限重启 | 通过 |

其他断言：空闲时宿主调用数为零；恢复通知携带原会话标识；未确定完成时不能自动确认；所有测试创建的线程、HTTP 服务和父/子进程在结束时关闭。

为避免测试真的等待数分钟，测试会推进临时库的 `next_at`，以及在测试进程中缩短 HTTP 等待。没有修改生产默认退避参数，也没有做一小时真实模型任务测试。模拟 Agent 根据真实文件记录补回执，不能据此宣称任意原生模型都不会误判完成状态。

## 仍然保留的边界

本次是开发和模拟验证，新功能需要之后加载新版客户端；HTTP 的完整恢复状态及积压提示需要新版服务，在线会话尚未热升级。

自动恢复的是消息传输和收件提醒，不是任意宿主工具的全局 exactly-once 执行。没有证据判断副作用是否发生时保留任务并报告，不能为了继续队列而猜测 ACK 或重新执行。没有原生通知能力、未执行预挂命令、宿主/守护整体退出等情况，不能由普通后台进程凭空唤醒 Agent。未接通适配器和人工退出也不会被自动恢复改成在线。
