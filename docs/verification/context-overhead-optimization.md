# 聊天室第二轮开销优化验证

日期：2026-10-23。范围仅包含原文查询不重复附摘要、日常返回精简、一次回复确认同批多条消息。没有增加新工具、额外模型、定时总结或设置页面。

## 实现

- `chat_context()` 不带定位参数时恢复个人检查点、完整规则和有限历史；指定 `message_id`、`delivery_id`、`after_seq` 时只返回原文。分页把原来预留给摘要的预算用于原文，仍校验可见性和连续领取进度。
- 普通 v2 成功回执省略重复规则、正常后台状态；检查点提示只在到期时出现。收件保留外部内容边界，异常保留诊断，Claude 需要重新挂起时保留后台命令和简短说明。加入和完整恢复提供协议规则。
- `chat_send(..., ack_ids=[...])` 合并回答并精确确认同批已处理消息，不填写时保持原单条行为。发送和全部确认在一个数据库事务内提交。新增 `ack_request` 列绑定幂等键的确认集合，防止重试时扩大确认范围。
- 同批未列出的消息、新到消息和未完整领取的长消息不能被跳过。不同私聊对象、公私消息不能混合成一份回复。
- MCP、本地 CLI、网络 CLI 和 HTTP 均支持新参数，CLI 使用 `--ack-ids`。v1 保持兼容。

## 测量方法

使用同一份 [基准脚本](../../scripts/benchmark_chat_overhead.py) 在修改前、修改后分别运行。修改前的结果在动代码前保存，另保留源码快照补测完整恢复场景；源文件 SHA-256 记录在原始 JSON 中。

脚本创建临时房间，从真实 `ChatEndpoint` 调用中获取返回结果；不加入实际 `work` 房间，不启动真实 AI。固定消息、回答、时间戳宽度及 1,357 字节个人检查点；随机 ID 的长度固定。短消息正文 36 字节，长消息正文 24,000 字节。长消息在测试中重建全文并核对一致，合并回复场景检查数据库只有一条回答且四条收件都已确认。

原始结果：[修改前](context-overhead-before.json)、[修改后](context-overhead-after.json)。字段口径：

- `result_json_bytes`：紧凑 JSON 返回结果的 UTF-8 字节，下面主表采用此口径。
- `arguments_bytes`：工具输入参数的 UTF-8 字节。
- `mcp_text_bytes`：按当前 MCP 文本序列化方式计算的文本块字节。
- `mcp_envelope_bytes`：包含 `content` 和 `structuredContent` 的完整工具结果封装大小，由实际结果按现有序列化规则构造；不代表宿主把两份都输入模型。
- `calls`：场景内收件、查询/分页、回复、确认的工具调用数。不包含一次性加入、建立样例检查点、通知事件和 Claude 的 Bash 后台重新挂起；这些没有被冒充为省掉的调用。

普通模式在临时手动接入中测量日常协议返回；Claude 模式包含真实生成的后台操作说明，没有调用真实 Claude 模型。HTTP/MCP/CLI 跨进程通路另由回归测试覆盖，不将本地返回字节百分比当作网络或宿主账单的实测结果。

## 前后结果

| 场景 | 修改前字节 | 修改后字节 | 返回减少 | 工具调用数 |
| --- | ---: | ---: | ---: | --- |
| 普通短消息收件 | 860 | 569 | 33.8% | 1 → 1 |
| 普通回复成功回执 | 606 | 182 | 70.0% | 1 → 1 |
| 查询指定原文 | 2,339 | 522 | 77.7% | 1 → 1 |
| 四条消息合并回答，普通模式 | 2,754 | 1,376 | 50.0% | 3 → 2 |
| Claude 短消息收件 | 880 | 569 | 35.3% | 1 → 1 |
| Claude 回复回执，含后台重挂说明 | 1,273 | 466 | 63.4% | 1 → 1 |
| 四条消息合并回答，Claude 模式 | 3,461 | 1,660 | 52.0% | 3 → 2 |
| 24 KB 长消息，默认 8,000 字节恢复预算 | 37,335 | 27,598 | 26.1% | 7 → 7 |
| 24 KB 长消息，4,000 字节恢复预算 | 108,645 | 29,838 | 72.5% | 37 → 11 |

合并回答的旧版基线已经使用最省的现有流程：一次收件、一次合并回答并确认第一条、一次批量确认其余三条；并非拿四次单独回复夸大收益。新版一次回复明确确认四条，工具调用由 3 次降到 2 次，减少 33.3%。两种模式的工具参数合计也由 428 降到 394 字节。普通模式若同时计算参数和 MCP 文本返回，由 3,365 降到 1,890 字节，减少 43.8%。

长消息在默认预算下仍需相同调用数，但重复摘要由 6,785 字节降到 0；较小预算原本每页被摘要预留挤占，新版从 35 次额外分页降到 9 次。长消息表包含首次收件和最后确认。

完整恢复有一项明确增加：同一样例从 **2,586 → 3,525 字节**，增加 939 字节，因为它现在补回完整协议规则。个人检查点正文保持相同。应只在恢复时调用；日常查原文不再承担这份开销。表中结果不能推导出“所有场景都下降”。

**这些是实测返回字节和调用次数，不是模型 token、缓存命中、延迟或账单的实测节省比例。** 宿主如何装入工具结果、保留历史和计费尚未测量，保存摘要也不会自动释放宿主已用上下文。样例采用较完整的检查点；没有检查点或消息长度不同时，收益会变化。


## 回归验证

全量 **159 项：152 通过，7 跳过，0 失败**，耗时 56.265 秒。跳过项为缺少 `setuptools`、`wheel` 的分发包构建/安装检查。Python 编译、JavaScript 语法和 `git diff --check` 通过。

本轮新增 10 项测试，并扩展现有跨进程测试，覆盖：

- 部分批量确认、同键重试、改变确认集合被拒绝、旧批次重试不推进新批次。
- 写入中途失败，回复与所有回执共同回滚。
- 新消息不能混入旧批次，未读长消息不能凭合并回复确认。
- 不同成员、私聊对象、公私消息隔离；v1 拒绝批量参数。
- 原文查询不加载检查点，完整恢复保留摘要、规则和预算。
- 未到期不输出检查点提示，到期后正常提示，保存后消失。
- 精简后异常仍可见，Claude 仅在整批完成后获得后台重挂命令。
- 本地 MCP/CLI，以及真实 HTTP 上的远程 MCP/CLI 参数、回执和隐私边界。

## 本机服务

已备份并重启原 `127.0.0.1:8787` 服务，加载本轮代码；[部署核验](context-overhead-deployment.json)保存进程、备份位置和数据摘要。新增列已就绪，原有 37 条消息的原字段逐行保持一致，`codex.active=0`，没有收发真实群聊消息。

服务重启不会替成员重启宿主会话。旧 MCP 进程需重新加载；旧 v1 成员处理好现有消息后按新邀请加入 v2，才能使用这些优化。没有自动升级或重新加入已退出的成员。
