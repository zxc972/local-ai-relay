# AirRelay 与直接执行的真实 Agent token 对比

日期：2026-11-04。当前源码基线 `3f4867763f0d615236fa9588fd43f15f14d07fa9`。

## 结论

同一项小型代码修复任务，各做三次。直接执行平均 **109,613 token**；通过 AirRelay 接入、等待、收件、执行和回传，平均 **259,220 token**，为直接执行的 **2.36 倍**，平均增加 **149,607 token（136.5%）**。这里的总量包含缓存输入。

三次各 30 秒的无消息等待中，**模型请求为 0、token 增量为 0**。额外用量出现在接入和处理消息的模型回合中。

## 实验方法

- 真实 Codex CLI `0.166.0-alpha.5.1`，实际会话均为 `gpt-6.1-terra`、`max` 推理强度；macOS arm64。
- 两组使用相同 CLI 配置、初始代码和任务文本，独立临时工作目录；明确配置 `workspace-write` 并允许网络访问，以便连接本机测试 HTTP 服务。没有修改用户的客户端设置。
- 任务：修复 `total_paid_cents()`，仅累计已付款记录，校验非负整数并排除 bool，忽略其他记录。冻结 7 项测试，模型不能修改测试。
- 直接组：给任务 → 修改代码 → 运行测试 → 汇报。
- 聊天室组：使用当前 Executor 角色提示词和明确的 CLI 加入命令 → 接入临时房间并结束模型回合 → 普通后台进程等待 30 秒 → 测试用户发送相同任务 → command 适配器产生事件 → 宿主续接原 CLI 会话 → Agent 自行收件、修改、验证、回传。
- 三组顺序为直接/聊天室、聊天室/直接、直接/聊天室。未固定模型生成路径或缓存命中，保留实际命令查询和额外检查的用量。
- 使用真实 HTTP 服务、SQLite、后台监听进程、真实模型和文件修改。服务绑定随机端口；没有使用在线 8789 房间和真实在场成员。
- 本次使用受测的 command 事件适配器续接 CLI，不是桌面 IPC 适配器，也不是对所有原生客户端自动唤醒的验收。发送任务的是测试程序，不包含另一个指导模型的用量。

## 各次结果

总量 = 输入 + 输出；不额外叠加缓存输入或推理输出。

| 组别 | 直接执行 | 聊天室全过程 | 多出 token | 倍率 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 81,917 | 256,634 | 174,717 | 3.13 |
| 2 | 157,614 | 334,251 | 176,637 | 2.12 |
| 3 | 89,308 | 186,776 | 97,468 | 2.09 |
| 平均 | **109,613** | **259,220** | **149,607** | **2.36** |

平均倍率按三次总量之比计算。三次小样本说明这个流程的开销量级，不代表任意模型、任务或项目的固定倍率。

## 阶段与缓存明细

每次任务的均值，四舍五入到整数。

| 阶段 | 输入 | 其中缓存输入 | 未命中缓存的输入 | 输出 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 直接执行 | 108,206 | 89,728 | 18,478 | 1,407 | **109,613** |
| 聊天室：接入并进入待命 | 35,210 | 25,771 | 9,439 | 395 | 35,605 |
| 聊天室：空闲等待 30 秒 | 0 | 0 | 0 | 0 | **0** |
| 聊天室：收件、执行、验证、回传 | 221,206 | 210,304 | 10,902 | 2,409 | 223,615 |
| 聊天室全过程 | 256,416 | 236,075 | 20,342 | 2,804 | **259,220** |

收件、执行和回传属于同一个连续模型回合，合并统计，没有人为多加回合来拆分阶段。

直接组分别发起 5、7、5 次模型请求；聊天室组每次为接入 2 次、处理任务 8 次，共 10 次。这些请求包括工具往返后的再次推理。接入历史、协议返回、通知和回执也进入后续输入。第一组中，直接执行每次请求输入约 1.5–1.7 万 token；聊天室任务回合约 2.6–2.9 万。

未缓存输入均值为 18,478 → 20,342，输出为 1,407 → 2,804；多出的输入大部分命中缓存。**不能把总 token 的 2.36 倍当成扣费或订阅额度的 2.36 倍。** 本次没有测量账单扣费，也没有把缓存 token 当成免费。

## 用量与结果核验

- 使用 CLI 的 `turn.completed.usage`，不是工具结果字节数，也不是按文字长度估算。[官方 JSON 输出说明](https://learn.chatgpt.com/docs/non-interactive-mode)。
- 本版 CLI 在 resume 后返回的是该会话累计用量。接入回合单列，任务回合使用完成累计值减去接入累计值；已逐一与这六个测试会话的 `token_count` 记录核对，防止重复计入接入用量。
- 输出包含模型生成的用量，推理输出是其中一部分，不能再加一次。[官方 token 计数说明](https://developers.openai.com/api/docs/guides/token-counting)。
- 6 次修复均通过独立的 7 项测试复验，测试文件原文未改变。
- 3 个聊天室样本的接入和工作回合 session ID 一致；每条任务恰好收到 1 条关联回复，且对应回执已确认。
- 三段空闲等待均无事件、无新增模型回合；测试结束退出临时成员并关闭临时服务，在线 8789 服务保持可用。

## 调试过程与边界

正式三组之前保留了两次测试宿主调试记录：第一次事件通知写入沙箱外被拒绝；第二次 CLI 续接未显式保留写权限，收件失败。修正为工作目录内的通知文件、宿主事件续接，并在两种路径都显式保持相同工作区权限。没有通过放宽到全盘权限解决。

这两个未完成流程不纳入成功任务均值，实际 CLI 用量分别为 124,337 和 170,766 token，合计 **295,103 token**。正式样本用量共 **1,106,500 token**；两者都不包括编写和调试基准的本主聊天用量。

这个样例是短任务。接入发生一次，后续可复用，但后续消息仍会产生收件、回传和历史输入成本；不能直接按任务数平均推导长项目的最终倍率。本次没有测第二个任务复用同一成员后的边际成本。
