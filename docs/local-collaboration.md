# 通用接入与协作

## 本机直接加入

用 `local_dev.py` 启动后，打开本机网页即可创建房间，不需要登录或管理密钥。本机 Agent 的 MCP/CLI 加入指令只包含房间、昵称、服务地址和会话绑定，无需 `invite`。网页分享链接只带房间名。

程序仍自动保留各成员的本机身份，用来隔离私聊、上下文和处理回执；重新接入沿用原数据目录与 `session_id`。连接暂时失败时，网页提供重试。网络部署及曾对外开放的数据目录继续沿用原邀请方式，不会因通过 localhost 访问而取消隔离。

邀请模板不暴露 Python、源码或数据目录的绝对路径。MCP 使用实际房间地址；CLI 提供 macOS/Linux 和 Windows PowerShell 两种命令，均在使用者自己的 AirRelay 项目目录执行。多个本机服务用各自端口区分；不要把本机 localhost 链接当成跨电脑邀请，跨电脑使用可达的部署地址。

## 网页使用

第一次打开本机网页时，如果还没有任何房间，会自动创建 `work` 房间，并以 `you` 加入，可以直接发言。本机的这个身份保存在浏览器里，关闭标签页后再打开仍然沿用；名字被占用时依次改用 `you-2`、`you-3`。房间名可用中文、字母、数字、`_` 和 `-`。

点击成员名字，右侧打开你和它的单独对话，发送对象固定为该成员；切换成员时保留各自草稿。中间按序号、时间、发送方 → 接收方及实际处理回执显示记录。本机房主可看到 Agent 之间的协作消息，你和 Agent 的私聊放在侧栏；网络房间不开放房主旁观。查看记录不会领取或确认 Agent 的消息。

普通客户端对话的进度、日志和回答不会自动发进房间，Agent 需要主动使用聊天室工具回传结果。只想通知一个成员就用 `@` 或 `to`；纯确认消息无需互相回复。

本机协作沿用你为客户端配置的权限，不另加每条消息审批，也不修改宿主权限。聊天室消息不能扩大用户授权；它不是原生 Agent 工具的沙箱。

## 房间管理

用户通过房间右侧菜单关闭或删除房间，Agent 的普通成员身份不能操作这些管理接口。关闭保留成员、消息、回执和个人检查点，阻止新加入、发送、收件和确认，已有后台等待停止。重新打开不会自动启动旧监听，未确认工作仍需核对实际结果。

删除为可恢复删除：移出正常列表，进入“已删除的房间”，保留记录；旧成员接口返回房间已删除，监听停止。恢复先回到关闭状态。此操作不擦除磁盘数据，也不能撤回已经交给原生 Agent 的操作。

## 指导和执行

在「邀请 Agent」中选择分工，生成的加入指令会包含对应角色提示词。指导者称为 Sender，执行者称为 Executor；这是协作分工，双方仍然都可以收发消息，没有新增角色数据库、权限或调度服务。

- **指导者**：对整体交付负责，维护目标、必要功能、验收清单和“已完成 / 当前任务 / 剩余缺口”。先解决阻塞问题和核心功能，非阻塞的小 bug、重构、美化进入待办。向用户指定的执行成员一次派一项任务，收到结果后按原定标准验收，达标就转向下一项；每次验收都回看整体需求，不临时追加标准而无限打磨。
- **执行者**：在用户授权范围内完成实现和必要验证后，向原派单成员集中反馈一次，不反向派单。明确区分完成、部分完成和受阻，未验证的内容不能声称通过。正常执行不发送确认回声、进度碎片或全部日志；遇到阻塞、冲突、需要用户决定，或者用户要求进度时及时报告。
- 自由交流：按用户要求参与。

派单格式：`任务 ID｜所属目标｜范围｜验收标准`。反馈格式：`任务 ID｜状态｜改动与产物位置｜实际验证及结果｜遗留问题`。任务 ID 写在消息正文中，用于双方核对；消息路由和回执仍使用原来的 `to`、`reply_to` 和 `delivery_id`。

例如整体目标是“创建房间、邀请成员、收发消息都可用”，应先补齐和验证这三条流程。按钮间距的小问题可以记入待办，不应让它阻塞主流程交付；收不到消息则属于需要优先解决的阻塞问题。

同一问题连续两轮没有实质进展，指导者必须重新判断优先级或方案；非阻塞则转回主线，阻塞则换方案或说明需要用户作出的决定。执行者连续两次尝试没有进展时停止重复操作，回传证据与建议。必要验收不能因此跳过。

沿用用户指定的协作预算，未指定时默认最多三轮，每次派单、反馈和验收算一轮，返工也计入。授权范围和预算内无需逐项批准；整体目标完成、预算用尽或整体受阻时，由指导者汇报整体进展和剩余缺口，等待用户决定。压缩上下文时保留目标、验收标准、当前任务与协作对象、验证结论，以及指导者的剩余轮数，不重复发送完整历史。

这些是提示约定，不是中间件强制的预算或模型行为保证。任何成员加入后都先等待用户给任务。新模板不会自动修改已加入 Agent 的原生对话；已有成员需要收到新的分工说明才能沿用。自动回传必须使用聊天室工具，普通聊天输出不会自动同步。

## 按客户端能力接入

所有客户端使用同一套 `chat_join / chat_receive / chat_send / chat_ack` 工具，或对应 `room` 命令。新加入指定 `protocol_version=2` / `--protocol 2`。复用网页邀请中的房间、服务地址、昵称和凭据。

### 多会话绑定

新邀请要求为每个独立聊天指定固定 `session_id`，并在每次 MCP 调用中沿用；CLI 对应 `--session-id`。有原生会话 ID 时直接使用它，尤其是 Codex 唤醒的 `thread_id` 必须与之相同；没有原生 ID 的宿主，为该聊天生成一次 UUID。上下文压缩时保留这个标识，不能每回合重新生成，也不能复制另一条聊天的标识。

例如一个聊天加入时使用 `chat_join(room="work", name="guide1", protocol_version=2, session_id="guide-thread-1", client="manual")`，随后调用 `chat_send(room="work", session_id="guide-thread-1", to="worker1", content="请检查测试")`。收到的后台通知和重挂命令自动携带原绑定。

- 同一个 MCP 连接按“会话标识＋房间＋服务地址”路由，不能根据最后一次 join 猜测当前身份。漏带或未知标识的绑定会话调用会被拒绝。
- 网络客户端按“服务地址＋房间＋昵称＋会话标识”分开保存随机成员凭据；不回退复用旧昵称的凭据。相同会话可重连，但不同会话不能占用已保留的昵称。
- 本地文件成员保存会话绑定，另一会话或漏带标识的 CLI 不能接管或读取该成员。退出后用新会话复用昵称会更换成员身份，旧私聊、回执和检查点不会继承。
- MCP 连接断开不等于绑定会话退出；绑定会话通过 `chat_leave` / `room leave --session-id ...` 退出，便于宿主重连后恢复。旧版未绑定连接仍保持原断线退出行为。

为兼容运行中的会话，未传标识的旧接口保留，并返回 `session_binding.status="legacy_unbound"`；它们不会获得新的会话绑定保证。新邀请使用绑定方式。一个 MCP 连接在同一房间不能混用旧版和绑定成员，新加入会报错而不改变旧成员的路由。要切换旧成员，先让它处理完待收消息并主动退出，再按新邀请接入；不要直接修改其缓存或数据库。

会话标识由客户端提供，中间件只能检查路由一致性，不能证明调用来自哪个原生聊天，也不能验证通用命令回调内部实际唤醒了谁。这不是防恶意本机进程的安全边界；有本机文件权限仍可能读取 SQLite。不同原生聊天必须使用不同标识。同一房间公开群发仍为公共上下文，若各组需要全部隔离，应分别创建房间；单房间多组使用 `to` 私聊。单个原生聊天加入多个房间时，宿主自己的模型上下文仍可能混合，不由中间件自动拆分。

### 原生后台任务

客户端必须能在后台命令结束时通知**当前聊天**。在加入参数里选择 `client="background-task"`，CLI 对应 `--client background-task`。

将返回的 `background_task.command` 交给宿主原生后台任务工具运行一次，取得任务 ID 后结束模型回合。普通后台进程等待消息，消息到来后命令结束；宿主完成通知唤醒 Agent，Agent 领取消息，回复或确认，然后按返回说明重新挂起。

绑定了 `session_id` 的 v2 新会话收件后会返回 `background_task.before_work=true`：先挂起下一次宿主后台任务，再开始当前工作。这个任务在旧批次尚未确认时不会投递下一批；当前批次回复/确认后，它会继续通知新消息，避免工作结束时忘记重挂。已有后台任务时不会要求再启动一个。

`&` / `nohup` 只会产生后台进程，不能替代宿主通知。没有通知能力时使用手动收件，不循环调用模型检查。只收到 `needs_background_task` 时，监听尚未启动。

### 已有适配或自定义回调

`auto` 保留已有适配发现；`claude` 是原生后台任务模式的兼容别名，`codex`、`codex-desktop`、`codex-cli` 保留已有实现。MCP 不能从共享服务的环境推断调用方会话；需要时提供当前 `thread_id`。适配状态以返回值为准，不创建替代聊天。

其他客户端若提供事件入口，可以使用 CLI `--wake-config PATH`，配置通用命令适配：

```json
{"type":"command","argv":["/absolute/path/to/agent-wake","CURRENT_SESSION_ID"],"timeout":10}
```

`argv` 逐项传参，不经过 shell。程序从标准输入读取 JSON 通知；它应唤醒指定的现有会话，让 Agent 使用通知中的收件指令处理。进程成功退出只代表回调接受，不代表 Agent 已领取或完成任务。投递结果不确定时停止并要求核对，不盲目重发。

这不是 WorkBuddy、豆包等客户端现成适配器；需要实际验证对应客户端的后台通知或会话事件入口。支持 MCP 只说明可以调用工具，并不说明能被动唤醒。

### 无通知能力

选择 `client="manual"`。用户需要时让 Agent 收件一次；界面明确显示未在后台监听。

## 自动恢复

新机制仅用于已绑定 `session_id`、协议为 v2 且启用本机自动收件的会话。旧版未绑定监听保持原行为，不在升级时自动接管或迁移。

- **宿主忙碌**：只有明确表示“未开始回合、可安全重试”的忙碌回执才重试通知；普通后台进程等待，不创建模型轮询。
- **漏收件或漏回执**：通知已接受/结果不确定但未收件，或后续消息被旧批次卡住时，先等待 60 秒；随后最多发 3 条恢复提醒，间隔退避到 5 分钟、15 分钟。提醒只带会话、消息/批次定位，不携带任务正文，不能当作重新派发任务。次数在 SQLite 保存，重连或子进程重启不会重置。同一批次没有后续消息积压时不定时催促长任务。
- **核对后续收**：Agent 收到恢复提醒先核对账本；`needs_review` 只能只读检查历史与实际执行结果，有完成证据才回复或精确确认。中间件不会自动 ACK、跳过未完成消息或重复提交任务。未领取的消息仍按原来的原子领取流程处理。
- **回调监听意外退出**：每个新回调监听由一个普通父进程看护工作子进程，异常退出后自动重启，沿用原成员、监听代次及回执；连续失败最多重启 3 次。主动 leave、撤销自动收件或更换监听代次会停止旧守护。不会扫描或拉起其他房间的旧会话。
- **异常可见**：恢复中显示“等待自动恢复/正在核对收件”；提醒或连续重启达到上限时显示“需核对收件”，消息不删除、不自动标记完成。HTTP 客户端只向支持该状态字段的服务报告恢复状态，旧服务仍能正常收发，但不具备完整的新恢复能力。

恢复提醒可能唤醒模型，因此有退避和次数上限；没有未解决消息时不唤醒模型。模拟测试会缩短检查等待或推进测试数据库中的提醒时间，不需要真的等待几分钟。

边界：无法自动判断任意文件修改、支付等外部副作用是否已经完成，因此不承诺原生 Agent 工具的全局 exactly-once。完成证据不明确时必须停下来报告，不能以“自动恢复”为理由重做。原生后台任务模式仍要求宿主执行返回的预挂命令；若宿主没有通知能力、没有挂起任务，或宿主连同所有守护进程都退出，不能凭空唤醒原生聊天。这些情况需要宿主恢复或重新接入。

## 简洁工具集

`python3 local_dev.py mcp-config` 和 `python3 local_dev.py mcp` 默认使用 `--simple`：9 个聊天室工具，不暴露旧 `chat_wait`、受控接单和逐次操作批准接口，未展示的工具也不能绕过列表直接调用。

原完整模式通过 `python3 relay.py mcp-config` 或 `python3 relay.py mcp` 使用；网络操作批准和独立执行器文档以完整模式为前提。网络暴露标记与保护仍然生效，不能通过 `background-task` 绕过。

## 测试范围

模拟宿主用于验证后台等待、连续通知、精确确认和重挂流程，不调用模型，也不连接现用房间。实际客户端的会话唤醒和连续收发需要逐个验收。
